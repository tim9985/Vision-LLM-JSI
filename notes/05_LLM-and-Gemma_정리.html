A

Hugging Face · Token 관리

먼저 원격으로 감을 잡는다

최종 목표는 Jetson에서 LLM을 직접 돌리는 것이지만, 처음부터 로컬로 가면 모델 다운로드·메모리 관리·라이브러리 설정이 한꺼번에 걸립니다. 그래서 먼저 Hugging Face Inference Provider로 원격 추론을 해서 LLM 사용법만 익힙니다.

자연어 처리 방식특징

first_llm.py원격 추론 최소 코드
import os
from dotenv import load_dotenv
from huggingface_hub import InferenceClient

load_dotenv()                          # .env를 환경 변수로 로드
TOKEN = os.getenv("HF_TOKEN")
MODEL_ID = "google/gemma-3-4b-it"

client = InferenceClient(api_key=TOKEN)

response = client.chat.completions.create(
    model=MODEL_ID,
    messages=[{"role": "user", "content": "한 문장으로 오늘 저녁 메뉴 추천해줘."}],
    max_tokens=150,
    temperature=0.7,
)

print(response.choices[0].message.content)
POINT

temperature는 출력의 무작위성입니다 — 0에 가까울수록 결정적(같은 입력에 같은 답), 높을수록 다양해집니다. 06 세션에서 신호등 색을 판단할 때는 temperature=0.0을 씁니다.

B

Token과 Tokenizer

LLM이 실제로 보는 단위

Token

  • LLM이 텍스트를 처리하는 기본 단위
  • 단어 · 단어의 일부 · 문자
  • 각 Token은 숫자 ID로 변환

Tokenizer

  • 텍스트를 Token으로 분리
  • Token을 Token ID로 변환
  • 모델마다 다르다
tokenize.py2단계를 encode/decode 한 줄로
from transformers import AutoTokenizer

tokenizer = AutoTokenizer.from_pretrained(MODEL_ID, token=TOKEN)

text = "Vision-LLM Multimodal System"

# 방법 1 — 두 단계
tokens    = tokenizer.tokenize(text)
token_ids = tokenizer.convert_tokens_to_ids(tokens)

# 방법 2 — 한 번에 (권장)
input_ids = tokenizer.encode(text, add_special_tokens=False)

# 되돌리기
converted_tokens = tokenizer.convert_ids_to_tokens(input_ids)
restored_text    = "".join(converted_tokens).replace("▁", " ")   # 수동
decoded_text     = tokenizer.decode(input_ids)                       # 한 번에
Special Token — add_special_tokens가 하는 일
  • True로 두면 Token ID 리스트 앞에 하나가 더 붙는다
  • 그것이 <bos> — Beginning of Sequence, 입력의 시작점을 모델에게 알리는 특수 토큰
  • 실제 문자열에는 보이지 않지만 모델 내부에서는 명확히 구분된다
model_input.py모델이 실제로 받는 형태
inputs = tokenizer(text, return_tensors="pt")   # "pt" = PyTorch Tensor

inputs["input_ids"]          # 각 Token의 ID (bos 포함)
inputs["attention_mask"]     # 어떤 Token을 실제 입력으로 처리할지
inputs["input_ids"].shape

C

Context Window

한 번에 볼 수 있는 Token의 한도

Context Window는 LLM이 한 번에 참고할 수 있는 Token 범위입니다. 입력과 생성된 내용이 모두 포함되며, 한도를 넘으면 일부 내용은 사용할 수 없습니다.

Total Tokens = Input Tokens (Prompt) + Output Tokens (생성) ≤ Context Window
token_count.py목표 Token 수까지 텍스트를 늘리는 함수
def make_long_prompt(tokenizer, text, target_tokens):
    prompt = ""
    while True:
        prompt += text
        token_count = len(tokenizer.encode(prompt, add_special_tokens=False))
        if token_count >= target_tokens:
            break
    return prompt

prompt_0500 = make_long_prompt(tokenizer, base_text, 500)
prompt_4000 = make_long_prompt(tokenizer, base_text, 4000)
usage.py실제 사용량은 응답이 알려준다
print(f"Input Tokens  : {response.usage.prompt_tokens}")
print(f"Output Tokens : {response.usage.completion_tokens}")
print(f"Total Tokens  : {response.usage.total_tokens}")
POINT

짧은 한국어 문장 "LLM에 대해 설명해줘."가 약 10 Token입니다. Prompt를 길게 넣을수록 답변에 쓸 수 있는 Token이 줄어듭니다 — 로컬 Gemma를 n_ctx=2048로 띄우면 Prompt와 답변을 합쳐 2048이 한도라는 뜻입니다.

E

LLM의 Memory

기억하는 게 아니라 매번 다시 넣는 것

LLM은 이전 정보를 계속 기억하지 않습니다. 현재 답변은 Context 안의 정보만 참고하므로, 필요한 내용은 별도로 저장했다가 다시 Context에 포함시켜야 합니다.

방식유지하는 것장점단점
Full History모든 대화정보 손실 없음Token 폭증 → Context Window 초과
Sliding Window최근 N턴만Token 일정하게 유지오래된 정보를 잃는다
Summary Memory과거는 요약 + 최근은 원문둘의 절충요약 과정에 추가 호출 필요
memory.py세 방식의 핵심 차이만
from copy import deepcopy
from collections import deque

# ① Full History — 전부 그대로
full_messages = deepcopy(history)
full_messages.append({"role": "user", "content": question})
role, content = generate_response(full_messages)
full_messages.append({"role": role, "content": content})

# ② Sliding Window — deque(maxlen=)이 알아서 앞을 버린다
TURNS = 2
recent_history = deque(deepcopy(history), maxlen=TURNS * 2)   # 1턴 = user+assistant 2개
recent_history.append({"role": "user", "content": question})
role, content = generate_response(list(recent_history))   # deque → list 변환 필요

# ③ Summary Memory — 오래된 대화를 LLM에게 요약시켜 앞에 붙인다
old_history = history[:-(TURNS * 2 - 1)]

old_history_text = ""
for message in old_history:
    old_history_text += f"{message['role']}: {message['content']}\n"

summary_prompt = f"""
다음은 사용자와 AI의 이전 대화야.
이후 대화에서 필요할 수 있는 중요한 정보만 짧게 요약해줘.

대화:
{old_history_text}

요약:
"""
POINT

deque(maxlen=N)은 꽉 찬 상태에서 append하면 앞쪽이 자동으로 밀려납니다 — Sliding Window에 딱 맞는 자료구조입니다. maxlen=TURNS*2인 이유는 한 턴이 user + assistant 두 개의 message이기 때문입니다.

그리고 deepcopy를 쓰는 이유 — 세 방식을 비교하려면 원본 history가 변하면 안 되기 때문입니다.

local_gemma.py로컬 챗봇 최종 코드
from llama_cpp import Llama

MODEL_PATH = "src/models/Gemma4/google_gemma-4-E2B-it-Q4_K_M.gguf"
CONTEXT_WINDOW = 2048
MAX_TOKENS = 300

llm = Llama(
    model_path=MODEL_PATH,
    n_gpu_layers=-1,          # -1 = 모든 레이어를 GPU에 (가속 최대)
    n_ctx=CONTEXT_WINDOW,     # Context Window 크기
    n_batch=32,              # 한 번의 decode에서 처리할 최대 token 수
    n_ubatch=32,             # GPU/CPU가 한 번에 계산하는 token 묶음 크기
    verbose=False,
)

while True:
    user_input = input("무엇을 도와드릴까요?")

    if user_input.lower() in ["exit", "quit", "q", "종료"]:
        break

    response = llm.create_chat_completion(
        messages=[{"role": "user", "content": user_input}],
        max_tokens=MAX_TOKENS,
    )

    print(response["choices"][0]["message"]["content"])

가장 헷갈리는 지점

두 API는 messages 구조가 완전히 같지만 결과를 꺼내는 방식이 다릅니다 — 원격은 점(.), 로컬은 대괄호([]). 코드를 원격에서 로컬로 옮길 때 여기서 AttributeError가 납니다.

Section Project — Summary Memory 기반 로컬 챗봇
  • 위 local_gemma.py는 Memory-Less입니다 — 매번 messages를 새로 만들어 이전 대화를 잊습니다
  • E장의 Summary Memory를 붙이면 됩니다: 대화가 N턴을 넘으면 오래된 부분을 llm에게 요약시켜 system message로 앞에 붙이고, 최근 N턴만 원문으로 유지
  • n_ctx=2048이 한도이므로 요약 없이는 금방 Context를 넘깁니다 — 이 프로젝트의 존재 이유
